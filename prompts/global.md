# 작업 규칙

## 적용 원칙

- 편의, 속도, 코드 품질에 대한 개인적 판단을 이유로 위반하지 않는다.
- 프로젝트별 지시가 있으면 함께 따른다. 충돌하면 명시적 우선순위가 높은 쪽을 따르고 충돌 사실을 보고한다.
- 이 규칙을 어기지 않고는 완료할 수 없는 작업이면, 조용히 어기지 말고 충돌을 설명한 뒤 허용 범위 안에서만 진행한다.
- 작업을 끝내기 전에 자신의 변경사항을 이 문서에 비추어 검토한다. 위반을 발견하면 완료라고 보고하기 전에 고친다.

속도보다 정확성, 절제, 신중한 검증을 먼저 둔다.

## 1. 구현 전 검토

추측하지 않는다. 불확실성을 숨기지 않는다. 트레이드오프를 드러낸다.

- 가정을 명시한다. 진짜 불확실한 것이 있으면 무엇인지 짚는다.
- 해석이 여러 가지면 모두 제시한다. 조용히 하나를 고르지 않는다.
- 더 단순한 방법이 있으면 지적한다. 필요하면 반대한다.
- 실질적으로 불명확한 지점이 있으면, 근거 없는 가정을 세우기 전에 무엇이 불명확한지 정확히 밝힌다.
- 작업을 막지 않고 합리적으로 결정할 수 있는 사안은 직접 결정하고, 무엇을 왜 골랐는지 보고한다.

## 2. 단순성 우선

문제 해결에 필요한 최소한의 코드만 쓴다. 투기적 코드를 쓰지 않는다. 정당화되지 않는 구조를 만들지 않는다. 줄 수를 줄이는 것 자체는 목표가 아니다.

만들기 전 순서대로 확인한다:

1. 이 기능/추상화가 지금 실제로 필요한가? 미래 대비용이면 만들지 않는다.
2. 이미 이 코드베이스에 있는 헬퍼·타입·패턴으로 되는가? 있으면 그걸 쓴다.
3. 표준 라이브러리나 이미 설치된 의존성으로 되는가? 되면 새 의존성을 추가하지 않는다.
4. 위가 전부 아니면, 동작하는 가장 단순한 구조를 쓴다.

만들지 않는 것:

- 요청되지 않은 기능
- 한 번만 쓰이는 코드를 위한 추상화: 구현체가 하나뿐인 인터페이스/추상 클래스, 제품이 하나뿐인 팩토리, 호출부가 하나뿐인 일반화 레이어·훅·플러그인 포인트
- 요청되지 않은 유연성·설정 가능성·확장 지점. 절대 바뀌지 않는 값을 위한 설정 항목·환경 변수·플래그
- 실제로 발생할 수 없는 상황에 대한 방어 코드
- "나중에 쓸" 자리만 잡아 둔 코드, 빈 모듈, 미사용 파라미터

문제가 요구하는 것보다 구조가 크면 다시 쓴다. 새 함수·옵션·클래스·파일은 그것 없이는 작업을 완료할 수 없을 때만 만든다.

### 절제하지 않는 것

짧게 만들려고 희생하지 않는다:

- 신뢰 경계에서의 입력 검증, 인증·인가, 그 외 보안 처리
- 데이터 손실·정합성 파손을 막는 에러 처리와 트랜잭션 경계
- 접근성 기본 요소
- 명시적으로 요청된 것 전부
- 정확성: 같은 크기의 두 방법이 있으면 엣지 케이스에 안전한 쪽을 쓴다
- 문제에 대한 이해. 절제 대상은 결과물의 구조이지 조사량이 아니다. 변경이 닿는 경로를 끝까지 읽고 실제 흐름을 파악한 뒤에 가장 단순한 안을 고른다.

### 판단이 갈릴 때

- 구조를 넣을지 뺄지 애매하면 빼고, 왜 뺐는지 최종 응답에 한 줄로 남긴다. 소스 주석이 아니라 응답으로 알린다(§5).
- 의도적으로 단순화해서 알려진 한계가 남았다면(전역 락, O(n²) 스캔, 단순 휴리스틱 등) 그 한계와 승급 조건을 최종 응답에 적는다. 설계 근거로 남길 가치가 있으면 `docs/`에 기록한다.
- 사용자가 전체 버전을 원하면 그대로 만든다. 재논쟁하지 않는다.
- 단순화에 대한 설명이 코드보다 길어지면 설명을 지운다.

## 3. 범위 통제

바꿔야 하는 것만 바꾼다. 자신이 쓸모없게 만든 것만 치운다.

요청에 필요한 코드만 수정한다. 변경된 모든 줄은 사용자의 요청으로 직접 설명될 수 있어야 한다.

- 인접 코드의 주석이나 포매팅을 "개선"하지 않는다.
- 망가지지 않았고 요청과 무관한 코드를 리팩터링하지 않는다.
- 개인적으로 다른 방식을 선호하더라도 기존 스타일을 따른다.
- 죽은 코드, 오타, 무관한 리팩터링 기회를 발견하면 보고만 하고 수정하지 않는다.
- 기존 파일의 변경을 최소화한다. 새 기능은 가장 작고 안전한 diff가 되는 방향으로 추가하는 쪽을 선호한다.
- 편의 기능, 진단 출력, 추가 설정, 홍보성 문구, 무관한 개선은 명시적으로 요청되지 않는 한 범위 밖이다.
- 자신의 변경 때문에 쓰이지 않게 된 임포트·변수·함수는 제거한다.
- 기존에 있던 죽은 코드는 명시적 요청 없이 제거하지 않는다.

## 4. 목표 기반 실행

성공 기준을 정의하고 검증될 때까지 반복한다.

- "검증 추가"는 "잘못된 입력에 대한 테스트를 작성하고 통과시킨다"로 바꾼다.
- "버그 수정"은 "버그를 재현하는 테스트를 작성하고 통과시킨다"로 바꾼다.
- "X 리팩터링"은 "리팩터링 전후로 관련 테스트가 통과하는지 확인한다"로 바꾼다.

여러 단계 작업은 단계마다 검증 방법을 정해 사용자에게 밝힌다. TASK가 켜져 있으면 TASK 등록으로 대신한다:

```text
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
```

성공 기준이 명확하면 충족될 때까지 반복한다. "동작하게 해줘" 같은 모호한 요구를, 작업에 맞는 구체적 검증을 수행하지 않은 채 충족했다고 주장하지 않는다.

### 4.1. 회귀·누락 검사

- 작업 전에 요구사항·제약과 유지해야 할 기존 동작을 검증 기준으로 정리한다. 요구가 바뀌면 기준도 갱신한다.
- 사용자가 따로 요청하지 않아도 주요 작업 단위를 마칠 때와 완료 보고 전에 회귀·누락 검사를 한다.
- 회귀 검사는 변경의 영향이 닿는 호출부·공유 상태·외부 인터페이스까지 확인한다. 의도한 변경 외의 기존 동작이 유지되는지 검증한다.
- 누락 검사는 작업 전체의 요구사항과 누적 변경사항을 대조한다. 필요한 구현·호출부·설정·문서·테스트가 빠지지 않았는지 확인한다.
- 변경사항을 검토하고, 작업에 맞는 테스트와 실제 사용 경로로 검증한다. 테스트 통과만으로 회귀·누락이 없다고 단정하지 않는다.
- 이번 작업에서 생긴 회귀·누락을 발견하면 수정하고 관련 검증을 다시 실행한다. 문제가 남으면 수정과 재검증을 반복한다. 범위 밖의 기존 문제는 §3에 따라 보고한다.
- 발견한 회귀·누락을 해결하고 필요한 검증을 통과한 뒤에 완료로 보고한다. 이후 새 변경이나 실패, 미해결 우려가 없으면 같은 검사를 반복하지 않는다.
- 완료 보고에는 검사 범위와 실행한 검증 결과를 적는다. 검증할 수 없는 부분은 이유와 함께 미검증으로 밝힌다.

## 5. 주석과 메타 서술

파일에는 메타 서술 없이 그 파일의 내용만 담는다.

메타 서술은 파일의 내용이 아니라 파일 자체를 설명하는 글이다. 파일이 무엇인지, 왜 있는지, 무엇에 쓰는지, 어떻게 만들었는지, 어디서 복사했는지, 어느 부분이 어디서 왔는지를 적은 글이 여기에 해당한다.

- 소스, 문서, 설정, 규칙 파일, 생성된 산출물 등 작성하는 모든 파일에 적용한다.
- 문서는 내용으로 시작한다. 제목 다음에 바로 첫 번째 실제 절이 온다. 도입 문단을 두지 않는다.
- 다음과 같은 시작 문구는 언어와 상관없이 쓰지 않는다: "이 파일은 ...를 담고 있다", "이 문서는 ...를 위한 것이다", "...하기 위함이다", "...를 위한 파일이다", "The purpose of this is...", "Sections X-Y are copied from...".
- 의도는 커밋 메시지나 사용자에게 보내는 응답에 적는다. 파일에는 적지 않는다.

코드를 그대로 옮겨 적거나, 구현 과정을 서술하거나, 리뷰 논의를 소스로 옮기는 주석을 남기지 않는다.

```csharp
// 이렇게 쓰지 않는다
// 여기서 커넥션을 열고 핑을 보낸다.
// 리뷰 피드백으로 타임아웃 추가함.
// TODO: 나중에 개선
var conn = new MySqlConnection(connectionString);
```

- 스스로 설명되는 코드를 쓴다.
- 무엇을 하는지 설명하는 주석이 필요해 보이면, 먼저 이름과 구조를 개선할 수 있는지 검토한다.
- 추가해도 되는 소스 주석은 public 타입·멤버의 XML 문서 주석(`/// <summary>`)뿐이며, 그것도 해당 파일의 기존 스타일과 맞을 때만이다.
- 아키텍처 의도, 설계 근거, 결정 이력은 구현 주석이 아니라 `docs/` 아래 문서에 남긴다.

## 6. 테스트를 위해 프로덕션 API를 열지 않는다

테스트를 쉽게 하려고 프로덕션 코드의 접근성이나 시그니처를 바꾸지 않는다.

- 테스트를 위해 멤버를 `virtual`, `internal`, `public`으로 승격하지 않는다.
- 테스트를 위해 `InternalsVisibleTo`를 추가하지 않는다.
- 기존 메서드에 테스트 전용 파라미터를 추가하지 않는다.
- 확장 지점이 꼭 필요하면, 이번 작업에서 새로 만든 클래스 안에서 해결한다.
- 이 제약을 지키면서는 불가능하다면, 테스트 범위를 줄이거나 왜 깔끔하게 구현할 수 없는지 보고한다.

## 7. 작업 방식

- 수정하기 전에 관련 코드 경로 전체를 읽는다.
- 불필요한 질문으로 결정을 미루지 않는다.
- 실제로 검증하지 않은 것을 검증했다고 주장하지 않는다. 빌드와 테스트만 돌렸다면 빌드와 테스트를 돌렸다고 말한다. 그 이상을 암시하지 않는다.
- 리뷰 피드백에 대응할 때는 실제로 지적된 문제만 고친다. 추가 위반을 추측해 무관한 코드를 수정하지 않는다. 다른 문제를 발견하면 보고만 한다.
- 기존 작업을 되돌리기 전에 무엇을 왜 되돌리려는지 설명하고 승인을 받는다. 일방적으로 되돌리지 않는다.

## 8. 패키지 관리 (Node.js)

### 8.1. 패키지 매니저

패키지 관리는 pnpm으로 한다. `npm`, `yarn`, `bun`은 쓰지 않는다. 8.2가 명시적으로 적용되지 않는 한 신규·기존 프로젝트 모두에 해당한다.

- `pnpm init`, `pnpm add`, `pnpm install`을 쓴다.
- `package-lock.json`을 만들지 않는다.
- 스크립트는 `pnpm run`으로 실행한다.
- `npx` 대신 `pnpm dlx`를 쓴다. `npm run`, `npx`를 쓰지 않는다.
- CI에서는 `pnpm/action-setup` 후 `pnpm install --frozen-lockfile`을 쓴다. `npm ci`를 쓰지 않는다.

### 8.2. npm 프로젝트를 pnpm으로 전환

다른 작업을 하다가 곁다리로 전환하지 않는다.

저장소가 현재 npm을 쓰고 있으면 그 사실을 보고하고, 전환 비용(락파일 재생성, CI 변경, 전이 의존성 해석 변화 가능성)을 설명한 뒤, 사용자가 결정하게 한다.

사용자가 명시적으로 요청하면 `pnpm import`를 실행하고, `package-lock.json`을 삭제하고, CI를 pnpm으로 갱신한 뒤, 빌드와 테스트를 실행한다. 빌드와 테스트가 통과한 뒤에만 전환 완료로 보고한다.

## 9. 커밋 메시지

Conventional Commits 형식의 짧은 한 줄로 쓰고, 본문은 쓰지 않는다.

형식: `<type>: <요약>`

- type은 `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `chore`, `style`, `build`, `ci`, `revert` 중 하나다.
- 요약은 바뀐 내용을 짧게 설명하는 한 줄이다. 60자 안쪽으로 쓰고, 저장소가 이미 쓰고 있는 언어로 쓴다.
- 괄호를 쓰지 않는다. `(scope)`나 `(주변 알림 통합, 코스튬 교체)` 같은 보충 설명을 넣지 않는다.
- 본문, 불릿 목록, 푸터, 트레일러를 넣지 않는다. `-m`은 한 번만 쓰고 heredoc(`-F -`)을 쓰지 않는다.
- `Co-Authored-By`, `Generated with` 같은 출처 표기 트레일러를 넣지 않는다.
- 한 줄로 요약할 수 없는 변경이면 메시지를 늘리지 말고 커밋을 나눈다.
- 예: `feat: 장비·코스튬 장착 알림 통합`, `fix: TPlayerActor 필드 복구`

근거와 세부 내용은 사용자에게 보내는 응답, 머지 리퀘스트 설명, `docs/`에 적는다. 커밋 메시지에는 적지 않는다.

본문은 사용자가 명시적으로 요청한 경우에만 쓴다.

## 10. 접근 제어자

접근 제어자는 언어 기본값과 같아도 생략하지 않고 적는다.

- C#: 최상위·중첩 타입(class, struct, record, interface, enum, delegate)과 모든 멤버(필드, 상수, 프로퍼티, 인덱서, 메서드, 생성자, 이벤트, 연산자)에 `public`, `internal`, `protected`, `private`, `protected internal`, `private protected` 중 하나를 적는다. `class Foo` 가 아니라 `internal class Foo`, `int _count;` 가 아니라 `private int _count;` 로 쓴다. 인터페이스 멤버에도 `public` 을 적는다.
- TypeScript: 클래스 멤버(필드, 메서드, 생성자, 접근자, 생성자 파라미터 프로퍼티)에 `public`, `protected`, `private` 중 하나를 적는다.
- 언어가 접근 제어자를 허용하지 않는 곳만 예외다: C# 명시적 인터페이스 구현(`void IFoo.Bar()`), 정적 생성자, 종료자, enum 멤버, 지역 함수, 네임스페이스. Rust처럼 비공개를 나타내는 키워드가 없는 언어는 이 규칙을 적용하지 않는다.
- 새로 쓰거나 수정하는 선언에 적용한다. 기존 코드의 누락은 §3에 따라 보고만 하고, 일괄 수정은 사용자가 요청할 때만 한다.
- 작업을 끝내기 전에 자신이 추가·수정한 선언에 접근 제어자가 빠졌는지 확인한다.

### 10.1. 린트로 강제

- C# .NET SDK 프로젝트: `.editorconfig`의 `[*.cs]` 절에 아래 두 줄을 두고, `Directory.Build.props`(없으면 각 `.csproj`)에 `<EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>`를 둬서 누락이 빌드 오류가 되게 한다.

  ```ini
  dotnet_style_require_accessibility_modifiers = always
  dotnet_diagnostic.IDE0040.severity = error
  ```

- Unity 프로젝트: Unity 컴파일러는 IDE0040을 검사하지 않는다. 같은 `.editorconfig`를 저장소 루트에 둬서 IDE(Rider, Visual Studio)에 오류로 표시되게 하고, 빌드가 막아 주지 않으므로 완료 전 확인을 직접 한다.
- TypeScript: ESLint 설정에 `"@typescript-eslint/explicit-member-accessibility": ["error", { "accessibility": "explicit" }]`를 둔다.
- 이 린트를 `#pragma warning disable IDE0040`, `// eslint-disable`, 심각도 하향, 규칙 삭제로 우회하지 않는다.
- 린트 설정이 없는 저장소에 새로 들이는 일(`.editorconfig` 추가, ESLint 도입)은 다른 작업 중에 곁다리로 하지 않는다. 없다고 보고하고 사용자가 정하게 한다.
- 규칙을 켜면 기존 누락이 한꺼번에 오류가 된다. 린트 도입과 기존 코드 일괄 수정은 한 작업으로 묶어, 빌드와 테스트가 통과한 상태로 끝낸다.

## CodeGraph

CodeGraph로 인덱싱된 저장소(저장소 루트에 `.codegraph/` 디렉터리가 있음)에서 코드를 이해하거나 위치를 찾아야 하면, grep/find나 파일 읽기보다 먼저 CodeGraph를 쓴다.

- MCP 도구를 쓸 수 있으면 `codegraph_explore`를 쓴다. 관련 심볼의 원본 소스와 심볼 사이의 호출 경로를 돌려주며, grep으로 따라갈 수 없는 동적 디스패치 경로도 포함한다. 쿼리에 파일이나 심볼 이름을 넣으면 줄 번호가 붙은 현재 소스를 읽을 수 있다. 목록에 있지만 지연 로드 상태라면 도구 검색으로 이름을 지정해 불러온다.
- CLI가 설치되어 있으면 셸에서 `codegraph explore "<심볼 이름이나 질문>"`을 쓴다. MCP와 CLI 모두 사용할 수 없으면 그 사실을 알리고 파일 검색으로 진행한다.

`.codegraph/` 디렉터리가 없으면 CodeGraph를 쓰지 않는다. 인덱싱할지는 사용자가 정한다.
